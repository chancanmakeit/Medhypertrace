



Q：经过仔细分析MAST给出的这十四种故障类型之后，我觉得它们是否能被分成两个大类：一类是由于模型本身能力问题导致的模型固有故障，另一类才是真正的组织架构协作型故障？

A：你的划分很有启发性，但**不建议把 MAST 的十四种故障硬性二分为“模型固有故障”与“组织架构协作故障”**。更准确地说，MAST 主要按照**故障在 MAS 中的表现形式和发生位置**分类，而不是按照唯一根因分类。论文将故障组织为系统设计、智能体间失配和任务验证三类，并明确承认某些失败可能来自基础模型限制，同时也指出同一表面行为可能有不同根因。

## 一、你的二分法抓住了一个重要维度，但它不是 MAST 原本的分类维度

可以把你的想法理解为一个新的**根因分类轴**：

1. **模型能力相关故障**  
   例如事实性错误、推理错误、指令遵循失败、上下文理解不足、社会推理不足。

2. **系统组织与协作相关故障**  
   例如角色设计不当、通信协议不完善、状态管理失败、验证流程缺失、终止机制设计不合理。

这个根因轴对于诊断和干预非常有价值。但它与 MAST 的三类故障并不一一对应。比如：

- “不遵守任务规范”可能是模型没有理解指令，也可能是任务规范含糊；
- “忽略其他 agent 的输入”可能是模型能力不足，也可能是消息路由、上下文压缩或决策权设计有问题；
- “没有验证”可能是系统根本没有验证模块，也可能是验证 agent 没有遵守职责；
- “错误验证”可能源于验证器的推理能力不足，也可能源于错误的验证标准。

论文对 FM-1.1 和 FM-1.2 的分析已经明确指出，它们的深层原因可能同时来自 MAS 设计、用户规范和基础 LLM 限制。

因此，**MAST 标签回答的是“发生了什么故障”，而你的二分法回答的是“故障主要由什么层面造成”**。两者最好作为两个独立字段，而不是互相替代。

## 二、十四种故障可以怎样放到这个新框架中？

下面是一种较为合理的“倾向性映射”。这里的“模型相关”不是说故障必然由模型造成，而是说该模式更容易受到模型能力影响。

| MAST 模式                  | 更可能涉及模型能力的一面               | 更可能涉及系统组织的一面               |
| -------------------------- | -------------------------------------- | -------------------------------------- |
| FM-1.1 不遵守任务规范      | 指令理解、约束遵循、事实与任务推理     | 规范含糊、提示设计差、任务状态管理不足 |
| FM-1.2 不遵守角色规范      | 角色理解、行为约束能力                 | 角色边界、权限和工作流设计不清         |
| FM-1.3 步骤重复            | 规划、记忆、状态跟踪能力不足           | 缺乏进度表、去重机制或状态机           |
| FM-1.4 对话历史丢失        | 长上下文理解和记忆能力                 | 上下文截断、消息存储和恢复机制         |
| FM-1.5 不知道终止条件      | 目标判断、停止决策能力                 | 终止协议、完成标准和监督机制           |
| FM-2.1 对话重置            | 上下文连续性和恢复能力                 | 会话生命周期、重试与状态恢复设计       |
| FM-2.2 未请求澄清          | 不确定性识别、主动沟通能力             | 没有澄清协议、升级机制或责任分配       |
| FM-2.3 任务偏航            | 目标保持、规划和自我纠错能力           | 子任务分解、全局监督和重新规划机制     |
| FM-2.4 信息隐瞒            | 信息选择、沟通意图和“他者需求”推理能力 | 消息格式、共享状态和信息披露机制       |
| FM-2.5 忽略其他 agent 输入 | 阅读、整合和冲突处理能力               | 决策权、消息优先级和反馈闭环设计       |
| FM-2.6 推理—行动不匹配     | 工具调用、计划执行和动作映射能力       | 接口约束、动作确认和执行控制机制       |
| FM-3.1 过早终止            | 完成判断和风险意识                     | 终止条件、监督者和退出流程             |
| FM-3.2 无或不完整验证      | 验证意识和任务风险判断                 | 验证模块、检查点和测试流程缺失         |
| FM-3.3 错误验证            | 推理、证据评估和批判性判断能力         | 验证标准、测试覆盖和验证器架构错误     |

这张表表明，**几乎没有一个模式能够稳定地归入单一大类**。尤其是 FM-1.1、FM-1.2、FM-1.5、FM-2.2、FM-2.5、FM-3.2 和 FM-3.3，通常都具有明显的双重归因可能性。

## 三、哪些故障更接近“模型固有故障”？

如果必须概括，以下模式更容易呈现为模型能力瓶颈：

- 事实性幻觉；
- 复杂推理错误；
- FM-2.2 中无法识别信息不足；
- FM-2.5 中无法理解或整合其他 agent 的建议；
- FM-2.6 中推理与行动不一致；
- FM-3.3 中无法判断验证证据是否足够。

特别是论文对 FC2 的解释认为，单纯改善上下文或通信格式可能不足以解决问题，因为这些失败涉及 agent 是否能够推断其他 agent 的信息需求，即更深层的“社会推理”能力。

但是，即使这些模式通常受模型能力影响，也不能因此认定系统设计无关。例如，要求 agent 显式声明不确定性、强制引用证据、使用结构化消息或引入冲突解决协议，都可能显著改变故障率。

## 四、哪些故障更接近“组织架构协作故障”？

以下模式更容易由系统设计直接触发：

- FM-1.3：没有进度状态或去重机制；
- FM-1.4：上下文管理和记忆架构不足；
- FM-1.5：终止协议设计不足；
- FM-2.1：会话重置和状态恢复机制不完善；
- FM-2.4：通信内容和信息共享机制不足；
- FM-3.2：没有验证流程或检查点；
- 部分 FM-3.3：验证标准、验证层级或工具设计错误。

论文的干预结果支持这一点：在保持底层模型和用户任务不变的情况下，改进角色规范使 ChatDev 的整体成功率提升了 \(9.4\%\)；增加高层任务目标验证则使 ProgramDev 成功率提升了 \(15.6\%\)。这说明至少一部分失败可以通过系统工作流和验证设计改善，而不必首先更换基础模型。

但这些结果只能证明**系统干预有效**，不能证明所有剩余错误都属于模型固有问题。系统设计可能只是降低了模型错误暴露的概率，而不是消除了模型能力限制。

## 五、比二分法更好的模型：三层或二维分类

我更推荐把每条故障记录为三个互补维度。

### 第一层：表现型故障

直接使用 MAST 标签：

```text
phenotype = FM-2.5
```

表示系统表现为“忽略其他 agent 的输入”。

### 第二层：近端失效机制

记录具体发生了什么：

```text
proximal_mechanism = decision_agent failed to integrate corrective message
```

### 第三层：根因层级

允许多标签或概率分配：

```text
root_cause = [model_capability, communication_design]
```

并记录置信度：

```text
model_contribution = medium
architecture_contribution = high
```

也可以形式化为一个二维矩阵：

\[
\text{故障描述} = (\text{MAST表现型},\ \text{根因归因})
\]

其中：

\[
\text{根因归因} \in
\{\text{模型能力},\text{系统设计},\text{协作机制},\text{验证机制},\text{任务规范},\text{混合或不确定}\}
\]

例如：

```text
MAST phenotype = FM-3.2
root cause = verification architecture
model contribution = low
```

或者：

```text
MAST phenotype = FM-3.3
root cause = mixed
model contribution = high
architecture contribution = medium
```

这种表示方式比强制二分更适合真实轨迹，因为同一个故障可能是多个因素共同作用的结果。论文也指出，MAS 失败往往涉及 agent 行为与整体系统设计的复合效应，因此精确定位单一根因本身就很困难。

## 六、一个重要的反例：同一 MAST 标签可以来自不同根因

以 FM-3.2 为例：

### 场景 A：纯架构缺陷

系统没有 verifier，也没有测试步骤；任务要求输出经过事实核查的医学建议。

```text
MAST = FM-3.2
root_cause = verification_architecture
```

### 场景 B：模型执行缺陷

系统设计了验证 agent，也给出了验证规范，但验证 agent 没有执行规定的检查。

```text
MAST = FM-3.2
root_cause = instruction_following_or_agent_capability
```

### 场景 C：任务规范不完整

系统没有说明哪些事实必须验证，agent 因而没有验证。

```text
MAST = FM-3.2 or none
root_cause = unclear_specification
```

这三个轨迹拥有相同或相近的 MAST 表现型，却需要完全不同的修复方案。因此，**MAST 标签不能单独承担根因诊断功能**。

反过来也一样：同一个“模型能力问题”可能表现为不同 MAST 标签。例如，长上下文处理能力不足可能表现为：

- FM-1.4：丢失对话历史；
- FM-2.3：任务偏航；
- FM-2.5：忽略其他 agent 输入；
- FM-3.2：遗漏验证要求。

## 结论

你的二分法可以作为一个很有价值的扩展，但我会把它改写成：

> **MAST 的十四种故障是系统行为层面的表现型；“模型固有故障”与“组织架构协作故障”是对这些表现型进行根因分析的另一条分类轴。二者不应被视为互斥的两个 MAST 大类。**

更具体地说：

- 有些错误主要来自模型能力；
- 有些错误主要来自系统架构；
- 很多错误是模型能力与组织设计共同产生的；
- 还有些错误的根因证据不足，应该标为“不确定”，而不是强行二分。

这也与论文的总体结论一致：提高 MAS 可靠性可能需要从 agent 组织、工作流、协调机制到基础模型能力进行组合式改进，而不是只依靠扩大模型或只修改提示词。
